# Занятие 1. Что такое тест

## Часть 1. Зачем тесты

**Unit-тест** (модульный тест) — маленькая программа, которая проверяет **одну** функцию или компонент: «если дать вот это — должно получиться вот то».

Ты уже **пользовалась** тестами! Вся неделя 0 — это `solution.test.js`, которые ты делала зелёными. Сегодня ты научишься **писать** их сама.

Зачем, если можно проверить в браузере руками:

- **быстро**: сотня проверок за секунду, вместо «открыть, кликнуть, посмотреть» по одной;
- **ничего не забудешь**: случаи вроде «пустой массив» и «пропуск дня» проверяются **каждый раз**;
- **смело менять код**: переписала `calcStreak` — запустила тесты — сразу видно, не сломалось ли;
- **документация**: по тестам видно, как функция должна себя вести.

Это ответ на вопрос «Что такое unit-тест?»: проверка одного маленького кусочка программы в изоляции от остального.

### Какой код тестировать проще всего

**Чистые функции** (неделя 1, день 4): результат зависит только от аргументов, ничего не меняется снаружи. `calcStreak(doneDates, today)` — идеальный кандидат. Именно поэтому на неделе 6 мы сделали её отдельной чистой функцией с параметром `today`.

## Часть 2. Как устроен тест

Открой любой тест недели 0, например `week-00-js/day-3/solution.test.js`:

```js
import { describe, it, expect } from 'vitest'
import { getTotal } from './solution.js'

describe('getTotal', () => {
  it('считает общую сумму', () => {
    expect(getTotal(products)).toBe(6440)
  })

  it('для пустого массива возвращает 0', () => {
    expect(getTotal([])).toBe(0)
  })
})
```

| Часть | Что делает |
|---|---|
| `describe('имя', () => {...})` | группа тестов — обычно одна функция |
| `it('что проверяем', () => {...})` | один тест — один случай. Синоним — `test` |
| `expect(факт)` | что получилось на самом деле |
| `.toBe(ожидание)` | что должно было получиться |

Читается почти как текст: «**ожидаю**, что `getTotal(products)` **будет** 6440».

### Структура «подготовь — сделай — проверь»

Хороший тест обычно из трёх шагов (по-английски — Arrange, Act, Assert):

```js
it('увеличивает счётчик', () => {
  // подготовь
  const counter = makeCounter(5)
  // сделай
  counter.inc()
  // проверь
  expect(counter.value()).toBe(6)
})
```

### Красный → зелёный

Если ожидание не совпало — тест **красный**, и Vitest показывает разницу:

```
Expected: "1 234,50 ₽"
Received: "1 234,5 ₽"
```

Ты это уже видела много раз в неделе 0 🙂

## Часть 3. Матчеры — способы сравнить

| Матчер | Проверяет | Пример |
|---|---|---|
| `toBe(x)` | строго равно (`===`) — для чисел, строк, `true` | `expect(sum(1, 2)).toBe(3)` |
| `toEqual(x)` | равно **по содержимому** — для массивов и объектов | `expect(getTitles(p)).toEqual(['А', 'Б'])` |
| `toBeUndefined()` | `undefined` | `expect(findById(p, 99)).toBeUndefined()` |
| `toBeNull()` | `null` | |
| `toBeTruthy()` / `toBeFalsy()` | truthy / falsy | |
| `toContain(x)` | массив или строка содержит | `expect(dates).toContain('2026-11-05')` |
| `toHaveLength(n)` | длина | `expect(list).toHaveLength(3)` |
| `toThrow()` | функция выбрасывает ошибку | `expect(() => parse('x')).toThrow()` |
| `.not.` | отрицание | `expect(copy).not.toBe(original)` |

### ⚠️ `toBe` и `toEqual` для объектов

```js
expect({ a: 1 }).toBe({ a: 1 })     // ❌ красный — два разных объекта (ссылки!)
expect({ a: 1 }).toEqual({ a: 1 })  // ✓ содержимое одинаковое
```

Ссылки из дня 2 недели 0 снова здесь. Для массивов и объектов — `toEqual`. А `toBe` с объектами полезен, когда нужно проверить, что это **тот же самый** объект (или, через `.not.toBe`, что это копия — как в тестах `copyObject`).

### ⚠️ `toThrow` — функция, а не вызов

```js
expect(parse('x')).toThrow()          // ❌ ошибка выбросится ДО expect — тест упадёт
expect(() => parse('x')).toThrow()    // ✓ передали функцию, expect вызовет её сам
```

Знакомая ловушка «передать функцию, а не вызвать» — как `addEventListener` из недели 0.

## Часть 5. Таблица случаев: `it.each`

На неделе 6 у тебя была таблица случаев для серии дней. Писать по `it` на каждую строку — много повторов. Для этого есть `it.each`:

```ts
import { describe, it, expect } from 'vitest'
import { percent } from './percent'

describe('percent', () => {
  it.each([
    [0, 10, 0],
    [5, 10, 50],
    [10, 10, 100],
    [3, 0, 0],      // делить на ноль нельзя
  ])('percent(%i, %i) = %i', (done, total, expected) => {
    expect(percent(done, total)).toBe(expected)
  })
})
```

- в `each` — **массив случаев**, каждый — массив аргументов;
- в названии `%i` (число), `%s` (строка), `%o` (объект) подставляются значения — чтобы по названию было понятно, какой случай упал;
- функция теста получает элементы случая как параметры.

Ты видела такой тест в неделе 0: `describeType` проверялся именно через `it.each`.

# Занятие 3. Время в тестах и что тестировать

## Часть 6. Время в тестах

Если функция берёт `new Date()` **внутри** (как `todayKey()`), тест зависит от реального дня — сегодня зелёный, завтра красный. Два решения.

### 1. Передавать «сегодня» параметром

Как в `calcStreak(doneDates, today = new Date())`. Самый простой и понятный способ. Параметр по умолчанию — чтобы в обычном коде не нужно было его передавать.

### 2. Подделать время в тесте

Если функцию менять не хочется, Vitest умеет **подменять часы**:

```ts
import { vi, afterEach } from 'vitest'

afterEach(() => {
  vi.useRealTimers()        // вернуть настоящее время после каждого теста
})

it('todayKey возвращает дату в местном времени', () => {
  vi.useFakeTimers()
  vi.setSystemTime(new Date(2026, 10, 6, 1, 30))   // 6 ноября, 01:30 ночи
  expect(todayKey()).toBe('2026-11-06')            // ловушка toISOString из недели 4!
})
```

Ты видела `vi.useFakeTimers()` в тестах `delay` из недели 0.

⚠️ Не забывай `vi.useRealTimers()` — иначе поддельное время «протечёт» в следующие тесты.

Тест на 01:30 ночи — отличная проверка той самой ловушки с `toISOString` из дня 3 недели 4. Напиши его!

## Часть 7. Что тестировать

| Тестировать | Не тестировать |
|---|---|
| **чистые функции** с логикой: серия, процент, форматирование дат | сам Vue: «`ref` меняется» — это проверили создатели Vue |
| **граничные случаи**: пустой массив, ноль, конец месяца | тривиальное: функция, которая возвращает константу |
| то, что уже **ломалось** | чужие библиотеки |
| логику стора: действия и геттеры | внешний вид (цвет, отступы) |

Правило: **тестируй то, где можно ошибиться.** Если ошибка в функции однажды уже случилась — напиши на неё тест, чтобы она не вернулась.

### Тест для стора (бонус)

Действия и геттеры стора тоже можно тестировать без компонентов:

```ts
import { setActivePinia, createPinia } from 'pinia'
import { beforeEach, it, expect } from 'vitest'
import { useHabitsStore } from './habits'

beforeEach(() => {
  setActivePinia(createPinia())   // новый «чистый» Pinia перед каждым тестом
  localStorage.clear()
})

it('addHabit добавляет привычку', () => {
  const store = useHabitsStore()
  store.addHabit({ title: 'Зарядка', category: 'Здоровье' })
  expect(store.habits).toHaveLength(1)
})
```

⚠️ Если стор использует `localStorage`, тестам нужно браузерное окружение — завтра настроим `jsdom`, как в тестах недели 0 (`// @vitest-environment jsdom`).

## Часть 8. 📜 Тесты и Options API

Тесты **чистых функций** и **стора** не зависят от стиля компонентов совсем: `calcStreak` одинакова везде, а options-стор тестируется точно так же, как setup-стор (`setActivePinia` + вызов действий).

Разница появится завтра, в тестах **компонентов**: монтируется компонент одинаково, но заглядывать «внутрь» удобнее по-разному. Об этом — в части про Options API завтра.

|---|---|
| Unit-тест | проверка одной функции или компонента в изоляции |
