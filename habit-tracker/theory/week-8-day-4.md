# Занятие 1. Lighthouse и доступность

## Часть 1. Lighthouse

**Lighthouse** — встроенный в Chrome инструмент, который проверяет сайт и ставит оценки от 0 до 100:

| Категория | Что проверяет |
|---|---|
| **Performance** (производительность) | как быстро страница загружается и становится удобной |
| **Accessibility** (доступность) | удобно ли пользоваться людям с особенностями зрения, без мыши |
| **Best Practices** (хорошие практики) | безопасность, ошибки в консоли, устаревшие API |
| **SEO** | понятен ли сайт поисковикам |

### Как запустить

1. Открой **опубликованный** сайт (не `localhost` — там код не сжат, оценка будет хуже настоящей).
2. DevTools → вкладка **Lighthouse**.
3. Режим **Mobile** (проверка как на телефоне — обычно строже), категории — все.
4. **Analyze page load** → подожди минуту.

⚠️ Расширения браузера влияют на результат. Лучше запускать в окне **инкогнито** (Ctrl + Shift + N), где расширения выключены.

### Как читать отчёт

- оценка **90–100** — зелёная, **50–89** — оранжевая, **0–49** — красная;
- под каждой категорией — список **замечаний** с объяснением и ссылкой «Learn more»;
- не гонись за 100 во всём — исправь **красное** и самое важное **оранжевое**.

## Часть 2. Частые замечания и как их исправить

| Замечание | Что значит | Как исправить |
|---|---|---|
| *Image elements do not have explicit width and height* | у картинок нет размеров — при загрузке страница «прыгает» | `width` и `height` у `<img>` или в CSS |
| *Image elements do not have [alt] attributes* | нет `alt` | `alt` с описанием (неделя 1, день 2) |
| *Buttons do not have an accessible name* | кнопка-иконка без текста (`✎`, `✕`) | `aria-label="Редактировать"` |
| *Background and foreground colors do not have a sufficient contrast ratio* | текст плохо читается | темнее текст / светлее фон; проверь **обе** темы |
| *Form elements do not have associated labels* | поле без подписи | `<label>` вокруг поля или `for` / `id` (неделя 2, день 3) |
| *Document does not have a meta description* | нет описания для поисковиков | `<meta name="description" content="…">` в `index.html` |
| *Browser errors were logged to the console* | ошибки в консоли | открой консоль и исправь |
| *Reduce unused JavaScript* | загружается лишний код | ленивая загрузка тяжёлых страниц (неделя 5, день 4) |

Для учебного проекта на Vite оценки обычно уже хорошие: Vite хорошо собирает, ленивая «Статистика» убирает Chart.js из первой загрузки.

## Часть 3. Доступность (a11y)

**Доступность** (accessibility, сокращённо a11y — между «a» и «y» 11 букв) — чтобы сайтом могли пользоваться **все**: люди с плохим зрением (большой масштаб, программы чтения с экрана), без мыши (только клавиатура), с дальтонизмом.

Это не «дополнительная фича», а признак качества — и вопрос, который часто задают на собеседованиях.

### Проверь сама

1. **Только клавиатура.** Убери мышь. Нажимай **Tab** — по очереди ли выделяются ссылки, кнопки и поля? Видно ли, **что** сейчас выделено? Нажимается ли кнопка по **Enter** / **пробелу**? Можно ли отметить привычку и добавить новую?
2. **Масштаб 200 %** (Ctrl + плюс). Ничего не наезжает и не обрезается?
3. **Без цвета.** Понятно ли, что привычка выполнена, если не различать цвета? (Галочка или зачёркивание — понятно; только зелёный цвет — нет.)

### Частые проблемы во Vue-приложениях

```vue
<!-- ✗ div, который «притворяется» кнопкой -->
<div class="btn" @click="remove">✕</div>

<!-- ✓ настоящая кнопка: фокус по Tab, Enter и пробел — бесплатно -->
<button type="button" aria-label="Удалить привычку" @click="remove">✕</button>
```

**Используй настоящие элементы**: `<button>` для действий, `<a>` / `RouterLink` для переходов, `<input type="checkbox">` для галочек. Они доступны «из коробки». `div` с `@click` не получает фокус по Tab и не нажимается с клавиатуры.

```css
/* ✗ никогда так не делай */
button:focus { outline: none; }
```

Рамка фокуса — то, по чему пользователь клавиатуры видит, где он. Если она некрасивая — **замени** своим стилем через `:focus-visible`, но не убирай.

# Занятие 2. Телефон и чистка кода

## Часть 4. Проверка на настоящем телефоне

### Через опубликованный сайт

Самый простой путь — открыть ссылку Netlify / Vercel на телефоне.

### Через локальную сеть (во время разработки)

Если телефон и компьютер в **одной Wi-Fi-сети**:

```bash
npm run dev -- --host
```

Vite покажет адрес вида `http://192.168.1.5:5173` — открой его на телефоне. Изменения в коде будут видны и там.

⚠️ Windows может спросить, разрешить ли доступ к сети для Node.js — это ты решаешь сама. Если разрешить не хочется — проверяй через опубликованный сайт.

### Что проверить на телефоне

- нет горизонтальной прокрутки;
- кнопки и галочки удобно нажимать пальцем;
- при фокусе на поле ввода страница не приближается (шрифт в полях ≥ 16px, неделя 7, день 5);
- тёмная тема: если на телефоне включена системная тёмная тема, `useDark` её подхватил?
- данные сохраняются после закрытия и открытия вкладки.

## Часть 5. Чек-лист чистки кода

Пройди по проекту:

**Консоль и отладка**
- [ ] нет `console.log`, оставшихся от отладки (поиск по проекту: Ctrl + Shift + F → `console.log`);
- [ ] в консоли браузера нет ошибок и предупреждений Vue;
- [ ] нет `<pre>{{ … }}</pre>` для отладки.

**Код**
- [ ] нет неиспользуемых файлов (`useHabits.js` после перехода на Pinia, старые компоненты);
- [ ] нет неиспользуемых импортов и переменных (VS Code показывает их бледным цветом);
- [ ] нет `// TODO`, которые уже сделаны;
- [ ] имена понятные: не `data2`, `temp`, `x`;
- [ ] нет `any` там, где можно указать тип;
- [ ] нет больших закомментированных кусков кода — для истории есть git.

**Проверки**
- [ ] `npm run type-check` — без ошибок;
- [ ] `npm run test:run` — всё зелёное;
- [ ] `npm run build` — собирается.

**Единообразие**
- [ ] один стиль кавычек и точек с запятой во всём проекте.

> Для единообразия есть **Prettier** — программа, которая сама форматирует код по правилам. А **ESLint** находит подозрительные места (неиспользуемые переменные, опасные конструкции). Если при создании проекта ты их включила — запусти `npm run lint` и `npm run format`. Если нет — можно добавить: `npm init @eslint/config` / `npm install -D prettier`. На работе они почти наверняка есть.

## Часть 6. 📜 Как читать чужой код (и рабочий проект на Options API)

Чистка своего кода — хорошая тренировка для **чтения чужого**. Вот порядок, который помогает разобраться в любом Vue-проекте, в том числе в рабочем:

1. **`package.json`** — версия Vue, какие библиотеки: роутер, Pinia или Vuex, UI-библиотека, VueUse.
2. **`main.js` / `main.ts`** — какие плагины подключены (`.use(...)`), есть ли глобальные компоненты (`app.component(...)`).
3. **`router/index`** — карта всех страниц приложения.
4. **`stores/`** (или `store/` для Vuex) — какие общие данные есть.
5. **Одна страница целиком** — от маршрута до дочерних компонентов.

Для каждого компонента на **Options API** задай вопросы по «полочкам»:

| Опция | Вопрос |
|---|---|
| `props` | что приходит снаружи? |
| `emits` | что сообщает родителю? |
| `data()` | какое у него своё состояние? |
| `computed` | что вычисляется? |
| `watch` | на что реагирует? |
| `created` / `mounted` | что делает при появлении (часто — загрузка данных)? |
| `methods` | какие действия умеет? |
| `mixins` | откуда ещё могли прийти данные и методы? |
| `setup()` | используются ли композаблы? |

Ты прошла **все** эти опции за курс, в каждом конспекте. Теперь любой компонент на Options API читается по этой таблице.
